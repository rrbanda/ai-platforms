Resource-Contention Protection
for Batch Spark Workloads

Validated POC — Kueue admission control eliminates the half-admitted failure mode for SparkApplications on RHOAI
Kubeflow Spark Operator 2.4.0 Red Hat build of Kueue 1.4.3 RHOAI 3.5.1 — OpenShift 4.19.9+

The Problem

Without admission control, a Spark job that requests more resources than available becomes "half-admitted" — the driver and some executors run, but the remaining executors stay Pending indefinitely. Resources are held for a job that can never complete. With a retry policy, this becomes a pod churn loop — tear down, retry, same stuck state, repeat.

The Solution

Kueue intercepts every SparkApplication at creation and computes the total resource demand across all pod sets (driver + all executors). If the demand exceeds available quota, the job is held in Suspended state — zero pods created, zero CPU consumed. The job waits in the queue until the full resource set can be reserved atomically.

1 Architecture

User / GitOps

oc apply -f sparkapplication.yaml
Submits SparkApplication CR with optional Kueue queue label

↓

Kueue Admission Controller

Mutating webhook intercepts SparkApplication. Computes total CPU/memory across all pod sets. Compares against ClusterQueue quota. Admits or suspends.

Spark Operator

Watches SparkApplication CRD. When spec.suspend = false, creates driver pod. Driver creates executor pods. Manages lifecycle.

↓

kube-scheduler

Schedules pods to nodes. With Kueue, only sees pods after admission — no partial scheduling.

2 Use Cases Validated

Use Case 1 — The Problem

Half-Admitted State

33 CPU SparkApplication submitted without Kueue. Driver + 1 executor run, 3 executors stuck Pending. 9 CPU wasted for a job that can never complete.

driver: Running | exec-1: Running | exec-2,3,4: Pending
Use Case 2 — The Solution

Kueue Admission Control

Identical job + one label. Kueue computes 33 CPU total demand, exceeds 8 CPU quota. Job held Suspended. Zero pods. Zero CPU consumed.

status: SUSPENDED | pods: 0 | cpu used: 0
Use Case 3 — Automatic Queuing

Quota Release & Re-Admission

Two 5-CPU jobs, 6 CPU quota. Job A runs, Job B waits. When A completes, B auto-admits in under 2 seconds. Zero manual intervention.

Job A: COMPLETED | Job B: RUNNING (admitted in ~2s)
Use Case 4 — Known Constraint

Dynamic Allocation Incompatibility

SparkApplication with dynamicAllocation.enabled: true and Kueue label is rejected immediately by the validating webhook.

Error from server (Forbidden): admission webhook denied
Use Case 5 — Resilience

Executor Failure & Auto-Recovery

Kill an executor mid-job. Spark driver detects the missing pod in ~30s, requests a replacement, retries tasks. Job completes with executionAttempts: 1.

exec-2: FAILED | exec-4: COMPLETED (replacement)

6 How Kueue Computes Spark Resource Demand

CPU Precedence:

coreRequest (preferred) → cores → default 1

Always set coreRequest explicitly to ensure Kueue's computation matches kube-scheduler.

Memory Overhead (Python):

max(0.4 × memory, 384Mi) added automatically by Kueue

Total Demand Formula:

driver_cpu + (executor_instances × executor_coreRequest)
