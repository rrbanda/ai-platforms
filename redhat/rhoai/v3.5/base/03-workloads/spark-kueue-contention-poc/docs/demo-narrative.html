Pre-Demo Checklist

⚠ Setup — Run 5 Minutes Before the Demo

Make sure the cluster is clean and manifests are ready:

# Verify you're logged in
oc whoami
oc project redhat-ods-applications

# Clean up any leftover SparkApps
oc delete sparkapplication --all --ignore-not-found

# Set ClusterQueue quota to 8 CPU
oc patch clusterqueue spark-cq --type merge \
  -p '{"spec":{"resourceGroups":[{"coveredResources":["cpu","memory"],"flavors":[{"name":"default-flavor","resources":[{"name":"cpu","nominalQuota":"8"},{"name":"memory","nominalQuota":"32Gi"}]}]}]}}'

# Verify Kueue is ready
oc get clusterqueue spark-cq
oc get localqueue spark-lq

# Verify Spark Operator is running
oc get pods -l app.kubernetes.io/name=spark-operator

Have two terminal tabs open — one for commands, one for oc get -w watches.

Opening — Tell

Set the Scene

~90 seconds. No terminal yet. Just talk.
🎤 Say This

"We've identified a specific failure mode that will become a real problem as we consolidate more batch Spark workloads onto a shared OpenShift cluster.

Here's the scenario: a Spark job is submitted that needs 33 CPUs total — one driver pod and four executor pods. But the cluster only has about 22 CPUs free across four worker nodes. What happens today, without any admission control?"

Pause. Let them answer or guess.

"The Spark Operator creates all five pods immediately. The kube-scheduler places what it can — the driver and maybe one executor — but the other three executors sit in Pending. The job is now half-admitted: partially running, partially stuck, holding resources for something that can never complete. If there's a retry policy, it gets worse — the operator tears everything down and tries again, creating the same stuck situation in a loop.

This is the exact pattern we saw with the deposits batch jobs. Let me reproduce it live, and then show you how Kueue eliminates it."

Demo 1 — Show

TC-1: The Problem ~2 min

Reproduce the half-admitted state WITHOUT Kueue
🎤 Say This

"This is a standard SparkApplication — Python SparkPi, 1 CPU driver, four executors at 8 CPU each. 33 CPU total. No Kueue label. Let's submit it and watch what happens."

⌨ Run This
oc apply -f /tmp/poc-contention/tc1-baseline-no-kueue.yaml

Wait ~15 seconds, then:

oc get pods -l sparkoperator.k8s.io/app-name=tc1-baseline-no-kueue -o wide
👀 You'll See
NAME                               READY   STATUS    NODE
tc1-baseline-no-kueue-driver       1/1     Running   ip-10-0-25-91
pythonpi-...-exec-1                1/1     Running   ip-10-0-25-91
pythonpi-...-exec-2                0/1     Pending   <none>
pythonpi-...-exec-3                0/1     Pending   <none>
pythonpi-...-exec-4                0/1     Pending   <none>
🎤 Narrate the Output

"Look at this — the driver is Running, one executor got placed, but three are Pending. Let me show you why."

oc get events --field-selector reason=FailedScheduling | tail -3

"Insufficient cpu. Every node is too full. The driver plus one executor are consuming 9 CPUs right now — held indefinitely for a job that will never complete with only 25% of its executors. This is the half-admitted state."

⌨ Cleanup
oc delete sparkapplication tc1-baseline-no-kueue
🎤 Transition

"So that's the problem. Now — same job, but we add one label: kueue.x-k8s.io/queue-name: spark-lq. This tells Kueue to manage it. Watch what's different."

TC-2: Kueue Blocks It ~1 min

Same job, Kueue-managed — SUSPENDED, zero pods
⌨ Run This
oc apply -f /tmp/poc-contention/tc2-kueue-admission-block.yaml
# Wait 5 seconds
oc get sparkapplication tc2-kueue-admission-block
👀 You'll See
NAME                        SUSPEND   STATUS      ATTEMPTS   START        FINISH
tc2-kueue-admission-block   true      SUSPENDED              <no value>   <no value>
⌨ Prove Zero Pods
oc get pods -l sparkoperator.k8s.io/app-name=tc2-kueue-admission-block
👀 You'll See
No resources found in redhat-ods-applications namespace.
🎤 Narrate

"Suspended. Zero pods. Zero CPU consumed. Here's what happened under the hood: Kueue's mutating webhook intercepted the SparkApplication at creation. It computed the total resource demand — 1 CPU driver plus 4 times 8 CPU executors equals 33 CPU. It compared that against the ClusterQueue quota of 8 CPU. 33 is greater than 8, so the job stays suspended. No pods are created. No resources are wasted. The job sits in the queue until quota is available."

"Compare that to what we just saw — same job, same cluster, completely different outcome. That's the core value proposition."

⌨ Cleanup
oc delete sparkapplication tc2-kueue-admission-block

TC-4: Automatic Queuing & Release ~3 min

Job B waits for Job A — auto-admits on completion, zero intervention
🎤 Set Up

"So Kueue blocks jobs that don't fit. But what about queuing? If I submit two jobs and only one fits, does the second one automatically run when the first one finishes? Let me show you."

"I'm going to set the ClusterQueue quota to 6 CPU. Each job needs 5 CPU — one driver plus two executors at 2 CPU each. So only one job fits at a time."

⌨ Run This
# Patch quota to 6 CPU
oc patch clusterqueue spark-cq --type merge \
  -p '{"spec":{"resourceGroups":[{"coveredResources":["cpu","memory"],"flavors":[{"name":"default-flavor","resources":[{"name":"cpu","nominalQuota":"6"},{"name":"memory","nominalQuota":"32Gi"}]}]}]}}'

# Submit Job A — runs immediately (5 < 6)
oc apply -f /tmp/poc-contention/tc4-job-a.yaml

# Wait 3 seconds, then submit Job B
sleep 3
oc apply -f /tmp/poc-contention/tc4-job-b.yaml

# Watch both
oc get sparkapplication -w
👀 You'll See — Initial State
NAME        SUSPEND   STATUS    ATTEMPTS   START                  FINISH
tc4-job-a   false     RUNNING   1          2026-10-20T03:12:01Z   <no value>
tc4-job-b   true      SUSPENDED            <no value>             <no value>

Then ~60 seconds later:

tc4-job-a   false     COMPLETED  1   2026-10-20T03:12:01Z   2026-10-20T03:13:02Z
tc4-job-b   false     RUNNING    1   2026-10-20T03:13:04Z   <no value>
🎤 Narrate As It Happens

"Job A is running — 5 CPU consumed. Job B is suspended — Kueue knows 5 plus 5 is 10, which exceeds the 6 CPU quota. So it holds Job B."

While waiting (~60s): "This is where you'd normally be monitoring a dashboard. The job is running SparkPi — it'll finish in about a minute. When it does, watch Job B."

When Job A completes: "There — Job A completed and look at Job B. It went from Suspended to Running within 2 seconds. Kueue automatically reclaimed the quota and admitted the next job in the queue. No manual intervention. No cron job checking. No operator on-call paging someone to restart the pipeline."

⌨ Cleanup
# Wait for Job B to complete (~60s), or Ctrl+C the watch and cleanup
oc delete sparkapplication --all --ignore-not-found

TC-5: Known Constraint ~30 sec

Dynamic allocation is incompatible with Kueue
🎤 Set Up

"One important constraint to document. In Hadoop, you're used to dynamic allocation — Spark scales executors up and down based on demand. With Kueue, that doesn't work. Kueue needs to know the exact resource footprint upfront to do its quota math. Let me show you what happens."

⌨ Run This
oc apply -f /tmp/poc-contention/tc5-dynamic-alloc.yaml
👀 You'll See — Immediate Rejection
Error from server (Forbidden):
  admission webhook "vsparkapplication.kb.io" denied the request:
  spec.dynamicAllocation.enabled: Invalid value: true:
  a kueue managed job can use dynamicAllocation only when the
  ElasticJobsViaWorkloadSlices feature gate is on and the job is
  an elastic job
🎤 Narrate

"Rejected at the webhook level — it doesn't even create the object. This means for Kueue-managed Spark jobs, you set executor.instances explicitly. You size your jobs upfront. That's the trade-off for getting admission control and gang scheduling — Kueue needs deterministic resource requests."

"For your batch ingestion workloads, this is fine — you know the data volume, you size the executors accordingly. Dynamic allocation is more relevant for interactive notebooks, which aren't Kueue-managed anyway."

Demo 5 — Show

TC-7: Executor Failure & Recovery ~4 min

Kill an executor mid-job — Spark auto-recovers, same as YARN
🎤 Set Up

"One question that comes up when migrating from Hadoop: what happens if an executor dies? In YARN, the ResourceManager replaces it. Does that work under the Spark Operator on Kubernetes?"

"Let me submit a long-running job — SparkPi with 5000 partitions, takes about 4 minutes. Once it's running, I'll kill one of the executors and we'll watch what happens."

⌨ Step 1 — Submit and Wait for Running
# Restore quota for this test
oc patch clusterqueue spark-cq --type merge \
  -p '{"spec":{"resourceGroups":[{"coveredResources":["cpu","memory"],"flavors":[{"name":"default-flavor","resources":[{"name":"cpu","nominalQuota":"8"},{"name":"memory","nominalQuota":"32Gi"}]}]}]}}'

oc apply -f /tmp/poc-contention/tc7-executor-failure.yaml

# Watch pods until all 4 show Running
oc get pods -l sparkoperator.k8s.io/app-name=tc7-executor-failure -w

Wait until you see 1 driver + 3 executors all Running, then Ctrl+C.

⌨ Step 2 — Kill an Executor
# Identify exec-2
EXEC_POD=$(oc get pods -l sparkoperator.k8s.io/app-name=tc7-executor-failure \
  --no-headers | grep exec-2 | awk '{print $1}')

# Kill it
oc delete pod $EXEC_POD --grace-period=0 --force
⌨ Step 3 — Watch the Recovery
# Watch pods — exec-4 should appear within ~30 seconds
oc get pods -l sparkoperator.k8s.io/app-name=tc7-executor-failure -w
👀 You'll See
# exec-2 disappears, then ~10-25 seconds later:
pythonpi-...-exec-1   1/1   Running   0   32s
pythonpi-...-exec-3   1/1   Running   0   32s
pythonpi-...-exec-4   1/1   Running   0   2s    ← replacement!
driver                1/1   Running   0   81s
🎤 Narrate

"exec-2 is gone. And there's exec-4 — the replacement. The Spark driver detected the missing executor through its Kubernetes pod allocator, requested a new one, and Kubernetes scheduled it. Tasks that were running on exec-2 get retried on the surviving executors. The job keeps going."

"This is the same fault tolerance model as YARN's ResourceManager, just using Kubernetes pod lifecycle instead of YARN containers. The Spark Operator doesn't handle this — the Spark driver itself does, through its built-in KubernetesClusterSchedulerBackend."

⌨ Step 4 — Wait for Completion and Verify
# Wait for COMPLETED (~3 min remaining)
oc get sparkapplication tc7-executor-failure -w

# Show final executor states
oc get sparkapplication tc7-executor-failure \
  -o jsonpath='{.status.executorState}' | python3 -m json.tool
👀 Final State
{
    "exec-1": "COMPLETED",
    "exec-2": "FAILED",       ← the one we killed
    "exec-3": "COMPLETED",
    "exec-4": "COMPLETED"    ← the replacement
}

Job status: COMPLETED, executionAttempts: 1 — no full-job restart.

⌨ Cleanup
oc delete sparkapplication --all --ignore-not-found
Closing — Tell

What We Just Proved

~2 minutes. Wrap it up with confidence.
🎤 Summary — Hit These Points
1
The problem is real and reproducible. Without admission control, a Spark job requesting more CPU than available becomes half-admitted. The driver and some executors consume resources for a job that can never complete. This scales linearly — more concurrent jobs, more wasted resources.
2
Kueue eliminates it completely. Same job, one label. The job stays suspended until the full resource set — driver plus all executors — can be reserved atomically. Zero pods created, zero CPU consumed, zero waste.
3
Queuing is automatic. When a running job finishes and releases quota, the next queued job is admitted within seconds. No cron, no manual restart, no pipeline orchestrator needed.
4
Executor fault tolerance works like YARN. If an executor dies mid-job — whether from a node drain, OOM kill, or spot preemption — the Spark driver replaces it automatically. Tasks retry on surviving executors. The job completes without a full restart.
5
The trade-off is fixed executor count. Dynamic allocation is not compatible with Kueue. You size your jobs upfront. For batch data ingestion where you know the volume, this is the right model.
🎤 The Ask

"For a production rollout — roughly 1,000 cores of batch Spark workloads — Kueue provides the guardrails to safely run concurrent jobs on a shared resource pool. The Spark Operator gives us the same fault tolerance as the YARN environment you're running today, with the added benefit of declarative, GitOps-friendly job definitions.

The manifests for everything you just saw are in the repo. Each test case is documented with the exact commands and expected output, so anyone on the team can reproduce this."

Likely Questions & Answers

💬 "What happens if the DRIVER dies, not just an executor?"

The restartPolicy on the SparkApplication controls this. With type: OnFailure, the Spark Operator recreates the driver and restarts the job from scratch. The executors go down with the driver — it's a full retry, not a partial recovery. With Kueue, the resubmitted job goes back through admission control.

💬 "Is Kueue + SparkApplication GA or Technology Preview?"

Technology Preview in RHOAI 3.5. The Spark Operator itself is GA (v2.4.0). The Red Hat build of Kueue Operator is GA. The integration between them — Kueue managing SparkApplication CRDs — is TP. The feature gate is SparkApplicationIntegration: true in the Kueue config.

💬 "How does Kueue know how much CPU a Spark job needs?"

Kueue reads coreRequest (preferred), then cores, then defaults to 1. For memory, it adds Python overhead: max(0.4 × memory, 384Mi). It sums across all pod sets — driver + every executor. Always set coreRequest explicitly so Kueue's computation matches what kube-scheduler will actually request.

💬 "Can we use ScheduledSparkApplication with Kueue?"

If the ScheduledSparkApplication template includes the kueue.x-k8s.io/queue-name label, each child SparkApplication it creates will be Kueue-managed. This is functional but not explicitly documented by Red Hat for RHOAI 3.5. We recommend testing it in the eLab before relying on it for production scheduling.

💬 "TC-2 and TC-3 look the same — what's the difference?"

Fair point. Both demonstrate Kueue blocking a job that exceeds quota. The distinction: TC-2 uses a 4 CPU quota (way too small), TC-3 uses 25 CPU (close — enough for the driver plus 3 of 4 executors). TC-3 proves Kueue won't partially admit — it evaluates the entire workload atomically, not pod-by-pod. The observable behavior is the same because Kueue's quota evaluation is inherently all-or-nothing for SparkApplications.

💬 "What's the queue wait time in production?"

In our testing, the re-admission latency was under 2 seconds after a job released quota. The bottleneck in production won't be Kueue's decision-making — it'll be how long the running job takes to complete. You can monitor queue depth and wait times through the Kueue Workload objects and ClusterQueue status.

💬 "Can we have multiple queues with different priorities?"

Yes. Kueue supports multiple ClusterQueues with different quotas, and you can organize them into cohorts for borrowing unused capacity. You can also set priority classes on workloads so higher-priority jobs jump the queue. This is out of scope for this POC but it's a GA feature of the Red Hat build of Kueue.
