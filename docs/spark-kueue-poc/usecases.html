Use Case 1 — The Problem

Half-Admitted State

What happens when a Spark job exceeds available cluster capacity — with no admission control
A SparkApplication requests 33 CPU (1 driver + 4 x 8 CPU executors). The cluster has only ~22 CPU free. Without Kueue, the Spark Operator creates all pods immediately. The kube-scheduler places what fits — the driver and one executor run, three executors stay Pending forever.

The job is half-admitted: 9 CPU held for a job that can never complete with only 25% of its executors.

Use Case 2 — The Solution

Kueue Admission Control

Same job, one label — Suspended, zero pods, zero waste
The identical SparkApplication now carries one additional label: kueue.x-k8s.io/queue-name: spark-lq.

Kueue intercepts the creation, computes the total resource demand across all pod sets (driver + all executors = 33 CPU), and compares it against the ClusterQueue quota (8 CPU). Since 33 > 8, the job is held in Suspended state. Zero pods are created. Zero CPU is consumed.

Use Case 3 — Automatic Queuing

Quota Release & Re-Admission

Job B waits while Job A runs — auto-admits on completion, zero intervention
Two Spark jobs, each requesting 5 CPU (1 driver + 2 x 2 CPU executors). The ClusterQueue quota is 6 CPU — only one fits at a time.

Job A is admitted immediately (5 fits in 6). Job B stays Suspended (5 + 5 = 10 exceeds 6). When Job A completes, Kueue automatically reclaims the quota and admits Job B — within less than 2 seconds. No cron job. No manual restart. No pipeline orchestrator.

Use Case 4 — Known Constraint

Dynamic Allocation Incompatibility

Kueue requires fixed executor count — dynamic scaling rejected at webhook
In Hadoop/YARN, Spark dynamically scales executors based on workload demand. With Kueue, this is not supported.

Kueue must know the exact resource footprint at admission time to perform its quota math. A SparkApplication with dynamicAllocation.enabled: true and a Kueue queue label is rejected immediately by the validating webhook.

The trade-off: set executor.instances explicitly. For batch data ingestion where you know the data volume and can size accordingly, this is the right model.

Use Case 5 — Resilience

Executor Failure & Auto-Recovery

Kill an executor mid-job — Spark driver replaces it, same as YARN
In YARN, the ResourceManager automatically replaces failed executors. Does the same work under the Kubernetes Spark Operator?

Yes. When an executor pod is killed mid-job, the Spark driver itself detects the missing pod, requests a replacement from Kubernetes, and retries affected tasks on surviving executors. The job completes with executionAttempts: 1 — no full restart needed.

Recovery time: ~25 seconds from kill to replacement executor running.
